# Session changes — 2026-08-27: universe restructure & scan efficiency

A working record of one session's changes: what was wrong, what changed, why, and what it should
do in practice. Written because it was asked for directly — this is a session log, not a
permanent reference doc like `ARCHITECTURE.md`/`STATUS.md` (which were also updated, and remain
the source of truth going forward).

---

## 1. The problems this session addressed

1. **The scan system was slow and the cause wasn't diagnosed.** The starting question was
   whether a long `universe.yaml` was the reason scans/data loading felt slow. It wasn't, not
   directly — `indexes:`/`watchlist:` were never read by the scan loop at all. The real driver
   turned out to be `would_own` (46 tickers, all scanned every 15-minute cycle) plus one
   undiagnosed cost hiding in plain sight (#3 below).

2. **No distinction between "core rotation" and "would accept, but not urgent."** All 46
   `would_own` names were treated identically: any of them moving 0.5% triggered a full
   option-chain re-fetch. There was no cheaper tier for names you'd sell a CSP on if the price
   were right, but don't need checked every 15 minutes.

3. **Held stock positions were fetched unconditionally every single cycle, regardless of
   movement.** This was the single biggest fixed IBKR cost in the loop and it predates this
   session — it just hadn't been named as the actual bottleneck until asked directly ("verify
   the actual bloat, cutting, and additions for the fetches to IBKR").

4. **The periodic safety-net sweep synchronized everyone together.** Every `force_full_scan_minutes`
   (120 min), the rule was "if the single *stalest* symbol in the core has gone unfetched too
   long, force-fetch the *entire* core" — meaning one quiet name could drag 18 perfectly fresh
   siblings into one synchronized burst of option-chain fetches in the same 15-minute cycle.

5. **Tickers the user will never trade were mixed into the live universe with no way to set them
   aside except deleting them outright** (losing the reasoning behind why they were added in the
   first place — IV ranges, collateral notes, risk flags).

6. **The Tier 1/2/3 labels didn't match how the user actually thinks about risk** (safe bets /
   moderate / risky), and — separately — didn't map cleanly to "what should be scanned constantly
   vs. only sometimes."

7. **TQQQ/UPRO couldn't be added, and SOXL couldn't move into `would_own`, without contradicting
   a documented safety rule** ("leveraged ETFs are NEVER `would_own`") that had no accommodation
   for a deliberate, informed exception — even though the user already trades CSPs on SOXL today.

8. **Sector ETFs were all scanned identically for CSP purposes despite very different premium
   quality.** XLF/XLK/XLE carry moderate-to-moderate-high IV and are worth the scan; XLV/XLP/TLT
   were flagged in the system's own research notes as "thin premium" / "rarely clears the IV
   gate" — i.e. scanned every cycle for a result that's usually a no-op.

9. **Nothing reacted to a large price move on a ticker outside the actively-scanned rotation.** A
   sharp drop on a name you'd genuinely accept assignment on could go unnoticed until someone
   manually ran `/scan TICKER`.

## 2. What changed

### `config/universe.yaml` — restructured

- Tier 1/2/3 renamed to **safe bets / moderate / risky** (organizational relabel only — the
  underlying groupings didn't change, since the user's own examples for each tier lined up with
  the existing groupings almost exactly).
- **8 tickers archived**: `ARKK, LLY, COST, CRM, COIN, MSTR, BITO, CRCL` — moved to a new,
  unloaded file (see below) instead of being deleted outright.
- **`would_own` trimmed and rebuilt from what was actually confirmed**, not guessed: went from 46
  broadly-included names down to a smaller confirmed core, then back up to 46 again as the user
  added back specific names (MAGS, NVDA, AMZN, SOFI, HIMS, NBIS) — the point wasn't the count, it
  was making sure every name in it reflects an actual decision.
- **New `actively_wheeling:` key** — a 19-name subset of `would_own`: the names actually checked
  every 15-minute cycle. Everything in `would_own` but not in `actively_wheeling` is "dip-watch"
  (see below).
- **XLV, XLP, TLT removed from `would_own` entirely** (kept in `indexes:` for tracking/CC-if-held)
  — the three flagged as thin-premium in the system's own research.
- **TQQQ, UPRO added; SOXL moved into `would_own`** — all three as a documented, deliberate
  exception to the "leveraged ETFs never `would_own`" rule, confirmed directly by the user
  ("I do sell CSPs on TQQQ, UPRO, and SOXL, so adding them to the list is genuinely ok for me").
  LABU/TSLL/DPST remain hard-excluded — the exception is scoped to exactly these three.
- `sectors:`/`strike_bands:` updated to match (new entries for MAGS/TQQQ/UPRO, archived tickers'
  entries removed).

### `config/universe_archive.yaml` — new file

Holds the 8 archived tickers with a one-line reason and date each. **Not loaded by the
application** — `src/common/config.py` only ever reads the four named config files
(`settings.yaml`, `risk_limits.yaml`, `scoring_weights.yaml`, `universe.yaml`), so this file has
zero runtime effect. It exists purely so a removed ticker's reasoning stays findable instead of
disappearing from the repo silently.

### `src/orchestrator/scan.py` — the materiality gate redesigned

`_compute_material_symbols` (the function deciding which symbols get an expensive option-chain
fetch each 15-minute cycle) now applies **three different thresholds** instead of one flat rule:

| Group | Size | Threshold | Direction |
|---|---|---|---|
| `actively_wheeling` (not held) | 19 | 0.5% move (`intraday_rescan_move_pct`) | either — unchanged from before |
| Held stock positions | varies | 2% move (`held_position_move_pct`) | **up only** (2026-08-27) |
| `would_own` minus `actively_wheeling` ("dip-watch") | 27 | 3% move (`dip_pull_in_pct`) | **down only** |

Plus: anything that cleared the score floor last cycle is always material, and anything with no
usable price baseline yet gets fetched once to establish one.

**Held positions used to be fetched unconditionally, every cycle, regardless of movement** — that
was changed first to a 2%-either-direction gate, then narrowed further to **up only**, since this
gate exists purely to refresh *new* covered-call candidate generation (a rally opens room to sell
a better OTM strike; a drop doesn't create that opportunity) — it has nothing to do with managing
your *existing* short calls, which the separate always-on event-driven daemon
(`src/monitor/intraday.py`) handles continuously regardless of this gate. A dropping held position
still gets refreshed eventually via the periodic staleness check below, just not instantly.

**Dip-watch names are not part of the per-cycle rotation at all.** They're cheap-probed (a single
price lookup, not an option-chain fetch) every cycle, and only get the expensive chain fetch when
they've *dropped* 3%+ — because a rally is never a reason to newly consider selling a put on a
name outside the core rotation. They're also excluded entirely from the periodic safety-net sweep
below (see §3).

### New config keys

`config/settings.yaml` / `src/common/config.py` → `market_data.held_position_move_pct: 0.02` and
`market_data.dip_pull_in_pct: 0.03`.

### Docs and tests

## 3. Deep dive: the per-symbol staleness check

This is the part worth walking through carefully, since it's a genuine behavior change and not
just a threshold tweak.

### The old rule

Every cycle, if `force_full_scan_minutes` (120) had passed, the code did roughly this:

```
oldest = the single OLDEST last-fetched timestamp across the whole core (actively_wheeling ∪ held)
if (now − oldest) > 120 minutes:
    force-fetch EVERY symbol in the core
```

The key word is **"every."** The check only ever looked at the single stalest symbol. If even one
name in a 19-symbol core hadn't been fetched in over two hours, **all 19** got force-fetched
together in that one 15-minute cycle — including symbols that had been fetched five minutes
earlier because they happened to be moving naturally.

### The new rule

```
for each symbol individually in the core:
    if (now − THIS symbol's own last-fetched timestamp) > 120 minutes:
        force-fetch THIS symbol
```

Each symbol's 120-minute clock now runs from **its own** last fetch, not the group's oldest
member. A symbol that keeps getting refreshed anyway (because it keeps moving 0.5%+ and tripping
the ordinary gate) never needs the safety net to fire for it at all.

### Concrete example

Say the core has three symbols — A, B, C — and the market opens at 09:30 with no prior baseline
(a genuine cold start forces everyone to fetch once, unconditionally, to seed the system; that
part is unchanged and unaffected by anything below).

Over the next two hours, suppose A happens to move 0.5%+ on its own at 10:15 (an ordinary,
already-existing gate firing — nothing to do with staleness) and gets refetched. Suppose B moves
and gets refetched at 10:45. Suppose C never moves at all in this stretch.

By the 11:30 cycle:

| Symbol | Last actually fetched | Age at 11:30 | Old rule | New rule |
|---|---|---|---|---|
| A | 10:15 | 75 min | forced anyway | **not** forced — 75 min < 120 min |
| B | 10:45 | 45 min | forced anyway | **not** forced — 45 min < 120 min |
| C | 09:30 (never moved) | 120 min | forced (correctly) | forced (correctly) |

**Old rule:** looks at the group, sees C is 120 minutes stale, forces all three → 3 option-chain
fetches this cycle, two of which (A, B) were pointless — they were already fresh.

**New rule:** checks each symbol against its own clock → 1 option-chain fetch this cycle (just
C), which is the minimum actually necessary.

From here forward the three symbols are on genuinely different schedules: C's clock resets to
11:30 (next due ~13:30), while A and B's clocks are still counting from 10:15 and 10:45
respectively. No single future moment forces all three together again unless, by coincidence, none
of them move at all for a very long stretch — which becomes less and less likely as the trading
day goes on and ordinary price movement keeps resetting different symbols' clocks at different
times.

### What this does and doesn't achieve — the honest version

- **It cannot make a symbol's own refresh cadence faster or slower.** Each individual symbol
  still gets, at most, one force-fetch per 120 minutes of its own inactivity — same as before.
- **It eliminates wasted "drag-along" fetches** of symbols that were already fresh, purely because
  a sibling was stale. That's a direct, real reduction in fetch count, not just smoother pacing.
- **It prevents synchronized bursts once the group has been running a while**, because ordinary
  price movement naturally desynchronizes different symbols' clocks over time (as in the example
  above). That matters operationally because a burst of many near-simultaneous option-chain
  fetches in one 15-minute cycle is exactly the load pattern that has previously caused real
  incidents in this system — a `qualifyContractsAsync` burst tripped an IBKR pacing lockout on
  2026-06-22, and a slow/overrunning cycle has separately caused later cycles to be skipped
  (tracked as "S9" in `STATUS.md`). Spreading the load avoids concentrating that risk.
- **The one honest limitation:** in the very first 120-minute window right after a cold start (or
  after a long gap, e.g. a weekend), or in a hypothetical session where *literally nothing* in the
  core ever moves, every symbol's clock started at the same instant — so the first forced sweep
  after such a start can still look synchronized, because there's been no natural movement yet to
  desynchronize anyone. The benefit is real but it accrues *over the session*, not instantly at
  cold start. Critically, the new rule is never *worse* than the old one in this case either — at
  worst it matches it (same one-time synchronized fetch), it just can't do better until real
  price movement starts happening.

## 4. Intended effect, summarized

| Lever | Before | After |
|---|---|---|
| Always-scanned core (subject to per-cycle gate + periodic sweep) | 46 | 19 (**−59%**) |
| Held-position chain fetch | every cycle, unconditional | only on a ≥2% **rise**, or no baseline |
| Dip-watch names (27) | scanned every cycle like everyone else | cheap price-probe only; chain-fetched only on a ≥3% **drop** |
| Periodic 120-min safety sweep | whole core force-fetched together if the stalest member expired | each symbol force-fetched independently on its own 120-min clock |
| Tickers never traded | mixed into the live universe | archived to a file the app never reads, reasoning preserved |
| TQQQ/UPRO/SOXL as `would_own` | blocked by an absolute rule | explicit, dated, reasoned exception |

None of this touches the risk gate, sizing, or the CSP eligibility allowlist itself — `would_own`
still means exactly what it always meant ("stocks you're genuinely comfortable being assigned"),
and every name that was would_own-eligible before this session still is. What changed is purely
*when* the system bothers to check.

## Addendum — 2026-08-28 follow-up (same universe rework, next day)

The numbers above (46 `would_own`, 19 `actively_wheeling`) are this session's own snapshot and are
now superseded — kept as-is above since this file is a dated log, not a living reference. The
following day, still working the same universe-efficiency thread, four more changes landed on top:

- **Further archive trim.** `would_own` cut from 46 to **32**; `actively_wheeling` from 19 to
  **17** (`GLD, XLF, XLK, XLE, XLU, XLI, SLV, MA, HD, AMD, NET, SNOW, TTD, DDOG` moved to
  `config/universe_archive.yaml`). See `ARCHITECTURE.md`'s `universe.yaml` row ("2026-08-28 trim")
  for the reasoning per name.
- **Bucket rules UNIONed, not selected between.** The old `if held / elif dip_watch / else` chain
  let `held` win outright, silently demoting a held `actively_wheeling` name to the 2%-up-only
  held gate instead of keeping its 0.5% either-way gate too — holding shares was accidentally
  *shrinking* coverage. Fixed in `_compute_material_symbols`; every applicable bucket rule is now
  tested and any one firing is enough.
- **Dip-watch seed-only at startup / manual `/scan`.** The full-sweep path no longer
  unconditionally chain-fetches all `dip_watch` names — each gets a cheap yfinance probe, and only
  a ≥3% overnight gap (either direction) earns the chain fetch; quiet names are seed-only
  (baseline persisted, `last_scanned_at=NULL`).
- **New per-cycle fetch budget**, `market_data.chain_fetch_budget_seconds` (600s) — caps how long
  one 15-min cycle spends chain-fetching, since the materiality gate's filtering collapses in a
  broad sell-off (every `would_own` name material at once). Symbols cut by the budget carry to
  `ScanResult.unreached_symbols` → next cycle's `must_include_symbols`, ranked first.

Full detail (this is the living version) is in `STATUS.md`'s "Intraday materiality gate (S1/S10)"
row and `ARCHITECTURE.md`'s `scan.py` row, both dated inline; `How the scan works.md` is the
operator-facing walkthrough and carries the current 32/17 counts throughout.
