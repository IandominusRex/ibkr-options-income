# System Architecture

A plain-English guide to how the system is built, what each part does, and how they connect.

---

## The big picture

Think of this system as a trading desk with several specialists who each do one job:

1. **Data Collector** — connects to Interactive Brokers and fetches live prices, option chains, and your account positions.
2. **Analysts** — calculate whether now is a good time to sell options on a stock (IV rank, technical trend, fundamentals, liquidity).
3. **Strategy Team** — generates specific trade candidates: "sell the AAPL July 200 call for $1.50".
4. **Risk Manager** — checks every candidate against hard rules before anything can proceed.
5. **Claude** — reviews the top candidates and writes a plain-English explanation of the tradeoffs.
6. **Telegram** — sends the candidates to your phone and collects your Approve/Reject response.
7. **Executor** — once you approve, re-checks the rules one more time with a live quote, then places the order.
8. **Intraday Watch** — monitors open positions during the day and alerts you when a roll is needed.

**You are the final decision-maker.** No order is ever placed without your explicit approval.

---

## How a trade happens (the pipeline)

```
IBKR live data
    ↓
Analytics (IV rank, technicals, fundamentals, liquidity)
    ↓
Strategy modules (generate candidate trades)
    ↓
Decision Engine (score + rank candidates)
    ↓
Rules Engine ← HARD STOP: enforces all risk limits, no AI involved
    ↓
Claude review (plain-English explanation, optional enrichment)
    ↓
Telegram → YOU approve or reject
    ↓
Rules Engine (re-checks with a fresh live quote) ← SECOND HARD STOP
    ↓
Order placed at IBKR (limit order at mid-price)
    ↓
Fill confirmation sent back to Telegram
```

Every step writes its results to the database. If any step fails, the system can resume from where
it left off. If Claude is unavailable, the pipeline continues without it — Claude enriches but
never blocks.

## Folder-by-folder guide

### `config/` — Tunable settings

These YAML files control how the system behaves. **You change behavior here, not in code.**

| File | What it controls |
|---|---|
| `settings.yaml` | IBKR connection (host, ports, client IDs), scan timing, execution timeouts, logging. The `claude` section also carries `backtest_in_prompt` (**C11**, default `false`) — whether a per-candidate on-demand backtest (`backtest/on_demand.py`) is injected into the strategist prompt as enrichment (off by default because it adds a yfinance fetch per candidate at prompt-build time) — and the N3 headless-subprocess hardening keys: `max_turns` (default `1`, a single agentic turn), `model` (pin the enrichment model id, e.g. `claude-sonnet-4-6`), and `disallowed_tools` (space-separated `--disallowedTools` denylist) so the unattended CLI can't drive tools or the filesystem. The local-LLM keys select and configure the Ollama backend: `backend` (`"cli"` code default, `"ollama"`, or `"cli_then_ollama"` — **this deployment runs `"ollama"`**, since `claude -p` isn't available), `ollama_host` (default `http://localhost:11434`), `ollama_model` (`qwen3:8b` here), `ollama_timeout_seconds` (default `120`), `ollama_num_ctx` (default `16384` — the requested context window; must cover the whole prompt *plus* the generated JSON or Ollama silently truncates one or both, dropping reviews), `ollama_keep_alive` (default `10m` — how long the model stays resident so a scan's successive calls skip reloads), and `ollama_temperature` (default `0.2`). The `scheduler.entry_cutoff` key (default `"15:00"`) sets the ET time after which the intraday loop stops surfacing new entries (profit-take checks still run until the close). The `automation` section holds the automated-trading circuit breakers: `max_auto_trades_per_day` (cap on new-exposure entry orders per ET day), `daily_loss_halt_pct` (auto-engage the kill switch when today's mark-to-market P&L, not fill cashflow, drops this % of net liquidation vs. the prior position snapshot — D3), and `drawdown_halt_pct` (auto-engage when net liquidation falls this % below its trailing high-water mark, catching a slow bleed no single day trips). The `execution.reprice_*` keys configure limit-order chase logic (`reprice_enabled`, default false; `reprice_interval_seconds`; `max_reprices`; `reprice_step_pct`) — when on, an unfilled order is repriced: entry SELLs step toward the bid (floor: `min_live_premium_ratio × approved premium`), buy-to-close BUYs step toward the ask, and roll BAG combos step the net-credit limit toward the live market (ceiling: `min_live_premium_ratio × approved credit`). The `market_data.strike_band_pct` (floor, default `0.15`), `strike_band_iv_mult` (default `1.5`), and `strike_band_max_pct` (cap, default `0.40`, S8) keys drive the IV-scaled strike band (N6): the auto-computed band is clamped to `[strike_band_pct, strike_band_max_pct]` so a high-IV ETF can't explode the qualified-strike/batch count; an explicit per-symbol `universe.yaml → strike_bands` override is not clamped. `monitor.roll_execution_enabled` (default `false`, N20) turns roll alerts into approvable roll candidates. **C4** adds `monitor.assignment_alert_delta` (default `0.70`) and `monitor.assignment_alert_dte` (default `21`) — the deep-ITM + DTE thresholds that trigger an assignment-risk alert. **D4** adds `monitor.roll_defensive` (`max_debit: 0.50`, `min_delta_reduction: 0.10`, `require_breakeven_improvement: true`) — the bounded-debit/delta-reduction economics `strategies/rolling.py::generate_roll_candidates` applies when called with `defensive=True` — and `monitor.manage_at_dte` (default `21`, the entry window's floor) — the mechanical close/roll/hold decision point, fired by `monitor/triggers.check_manage_at_dte` well before the 7-day gamma window (`dte_threshold`), while closing, rolling and explicitly holding are all still viable. `intraday.py` passes it into the `limits` dict `check_all` reads, so editing the key changes behaviour (it was defined and triggered on but never threaded through, so every alert silently used the hardcoded 21-day fallback). `market_data.max_concurrent_lines` is now enforced (N15): a `MarketDataCfg` validator fails config load if `chain_batch_size` exceeds it. `market_data.max_strikes_per_symbol` (default `80`, `0` disables) caps how many in-band strikes a symbol keeps (the N nearest spot) before the `strikes × expirations × 2` cartesian is built — a high-IV name at a wide band with dense ($2.50) spacing could otherwise yield 120+ strikes → a several-hundred-contract `qualifyContractsAsync` burst that floods IBKR with `reqContractDetails` for non-existent weekly strikes and trips a session-wedging pacing lockout (this hung the 2026-06-22 scan on SMH at 768 contracts). `market_data.qualify_timeout_seconds` (default `20`) bounds each qualification chunk: qualification is issued in `chain_batch_size` chunks paced by `request_throttle_seconds`, and a chunk that never resolves returns partial results instead of letting the outer `symbol_timeout` cancel the fetch mid-flight (that cancellation is what left the ib_async pipeline unable to service later symbols). `market_data.symbol_timeout_seconds` (default `90`) bounds how long `/scan` spends fetching one symbol's option chain — if IBKR never responds (pacing violation, error 10197 competing-session lockout), the symbol is skipped and the scan continues instead of hanging indefinitely; on timeout (or any chain error) the orchestrator calls `drain_market_data_lines` to reclaim any market-data lines the cancelled fetch left open against the ~100-line cap. `market_data.spot_history_timeout_seconds` (default `10`) bounds the `reqHistoricalData` fallback inside `_get_spot`/`_get_spot_async`, which is only reached when the snapshot has neither a live tick nor a previous close. The **half-dead-socket guards** (`market_data.health_probe_symbol`, default `SPY`; `health_probe_timeout_seconds`, default `15`; `max_consecutive_chain_timeouts`, default `3`, `0` disables) cover the case where TWS keeps its socket handshake up — so `ib.isConnected()` stays `True` and account summary resolves — but has lost its IBKR data farm (`Error 1100`), making *every* chain request time out; left unguarded, one intraday cycle grinds at `symbol_timeout_seconds` × the whole universe (~115 min) and starves every later 15-min cycle (the 2026-06-24 02:00 SGT stall). Before each intraday cycle `probe_market_data_health` fires one bounded snapshot quote on `health_probe_symbol`; mid-scan, `max_consecutive_chain_timeouts` back-to-back timeouts trip a circuit breaker that aborts the run (`ScanResult.aborted_unhealthy`). Either path notifies the operator on Telegram with the exact block reason and forces a reconnect (`ib_scan.disconnect()` → `AutoReconnect`). `market_data.intraday_rescan_move_pct` (default `0.005` = 0.5%) and `force_full_scan_minutes` (default `90`, `0` disables) drive the **S1 intraday materiality gate**: in the 15-min loop a `would_own` name is re-fetched only once its live spot drifts past `intraday_rescan_move_pct` from its last fetch; held names and names that cleared the score floor last cycle always fetch; and a full sweep is forced when the stalest fetched symbol exceeds `force_full_scan_minutes`. Manual `/scan` ignores the gate and always sweeps the full universe. |
| `risk_limits.yaml` | Per-ticker concentration limits, delta ranges, DTE windows, earnings blackout, minimum return. The `live_execution` section adds the send-time re-gate knobs: `min_live_premium_ratio` (reject a fill when the live mid has collapsed below this fraction of the approved premium — F2) and `require_ibkr_greeks_when_live` (in LIVE mode, require IBKR-sourced greeks for the delta gate — F6). `liquidity.morning_volume_cutoff_et` (default 10:30, N19) is the ET time before which the day-volume gate is skipped. `covered_call.min_strike_vs_basis` (default 1.00, N18) blocks below-cost-basis call writes — lower it to allow them on underwater holdings. **C1 IV/RV gate:** `iv.min_iv_rv_ratio` (default 1.05) — reject candidates where `current_iv / realized_vol < threshold`; `iv.realized_vol_window` (default 20 trading days) — the lookback window for the realized-vol denominator in the ratio. Missing ratio is treated as data unavailable and never blocks the scan. **`ideal_zone:` block (strike band + action levels are display/ranking-only; `min_credit_edge_pct` feeds a real gate — see below):** `em_lo_mult`/`em_hi_mult` (0.30/1.20) place the ideal strike band in expected moves — chosen to bracket the delta range actually traded (a 0.15–0.30Δ put sits at ~0.34–0.93σ, a 0.20–0.35Δ call at ~0.48–1.17σ); `earnings_widen_mult` (0.25) pushes it further OTM when earnings fall inside the option's life; `support_pull_pct` (3.0) is how close a support/resistance level must be for the band to snap to it — the snap moves the *outer* edge onto the level and the inner edge is then clamped back to `em_lo_mult`, so the band stretches rather than sliding toward spot (translating it used to drag the inner edge to at-the-money, reporting a ~0.53Δ covered call as "✓ in zone"); `min_credit_edge_pct` (10.0) is the premium demanded over Black-Scholes fair value at *realised* vol — the variance-risk-premium thesis made explicit, and (D2) the number `income.require_vrp_edge` gates on via `TradeCandidate.ideal.min_credit`; `buy_margin_of_safety_pct` (8.0) discounts the analyst mean target when placing the share-acquisition level. Consumed by `analytics/fair_value.py`, which itself never rejects anything — see `risk_engine.py`'s variance-risk-premium gate below for the code that does. **`income:` block:** `require_vrp_edge` (true) is the primary income gate — reject when `candidate.premium < candidate.ideal.min_credit` (reason `premium_below_fair_value`; a missing ideal zone is data-unavailable, never a rejection); `min_roc_pct` (0.15) / `min_annualized_yield_pct` (0.0) are now noise floors only — they used to be the primary gate, and `max(1.0%, 12% × DTE/365)` was a hidden ~25–30% IV floor that made every low-vol name (SPY, GLD, TLT, sector ETFs) permanently unreachable regardless of the actual variance-risk-premium edge (D2). **`portfolio:` block (D1, Task 9 — replaces the single `max_pct_per_ticker` that used to answer three unrelated questions at once, which is why any CSP above a ~$150 strike was unreachable at $300k NLV):** three constraints, each in its own unit, resolved by `engine/capital.resolve_caps` into a `Caps` object for one account snapshot. **Job 1, feasibility (cash):** `cash_reserve_pct` (20.0) and `cash_reserve_absolute` (10000) — the reserve held free at all times is the *greater* of a percentage of available cash (`account.excess_liquidity`) and the absolute floor; `max_csp_allocation_pct_of_deployable` (100.0) is total CSP collateral as a percentage of what's left *after* the reserve ("deployable cash"), not of gross cash or net liq. **The order of application is fixed in code, not configurable:** `deployable = available_cash − reserve` first, then `csp_budget = deployable × max_csp_allocation_pct_of_deployable`; expressing both against gross cash would let the two knobs contradict each other (the bug this replaces — the old `max_csp_allocation_pct: 60` was measured against net liq while only ~$100k of cash existed, so the budget could exceed the money). At $100k cash the reserve is `max(100000×0.20, 10000) = 20000` either way, but at a smaller account the absolute floor dominates and is *not* inert — e.g. at $16k cash, `max(16000×0.20, 10000) = 10000` (the 20% alone would have been $3,200). **Job 2, concentration (risk units — `collateral × IV × sqrt(DTE/365)`, so share price is not a risk measure):** `max_risk_units_per_ticker_pct` (5.0) and `max_risk_units_per_sector_pct` (25.0), both a percentage of net liq. **CALIBRATION WARNING (kept verbatim from the config comment):** risk units are collateral scaled by IV × √(DTE/365), typically 0.05–0.30, so these percentages are NOT comparable to the old collateral-based ones — 5.0 here is far more permissive than 5.0 was before. `max_risk_units_per_ticker_pct: 5.0` was examined, not assumed: `scripts/capacity_report.py` at $300k NLV / $100k cash shows AMD's single lot alone costs 3.06% of NLV in risk units (SMH 2.85%, NBIS 1.89%, QQQ 1.78%, META 1.77%) — the floor below which AMD becomes unreachable again — leaving only a 3.1–5.0 viable range; the human ruling kept 5.0, the permissive end. `max_collateral_per_ticker_pct` (10.0) is the fallback cap used when IV is unavailable, applied to raw collateral (strictly more conservative than the risk-unit cap) so a missing IV can never make a position *less* constrained. **Job 3, deliberateness (an explicit, counted slot):** `max_large_positions` (1) and `max_pct_per_ticker_large` (25.0, raw collateral % of net liq) — a position whose collateral exceeds `max_collateral_per_ticker_pct` needs a free large-position slot and must still sit under this hard ceiling; without it, a high-priced name is either impossible or unbounded, and one number can't express a third option. `max_margin_usage_pct` (50.0) and `max_new_positions_per_run` (10) are unchanged. Both `strategies/cash_secured_put.py` (`screen_csp_candidates`) and `risk_engine.validate_candidates` call the same `capital.max_contracts` helper, so the generator and the gate can never disagree about how big a position may be (the root cause of D1). Verify the effect of any change here with `python -m scripts.capacity_report` (see `SETUP.md`) — after Task 9 formalized these keys into config, 46/46 `would_own` symbols remained tradeable at $300k/$100k, unchanged from the in-code defaults `resolve_caps` had been using. |
| `universe.yaml` | Your watchlist (tickers to scan for CCs) and `would_own` list (stocks OK to be assigned via CSPs). Tickers are organised into three tiers: Tier 1 core (SPY/QQQ/AAPL/MSFT/NVDA/JPM/GLD/TSLA) plus sector-diversifier ETFs (XLF/XLK/XLE/XLV/XLP/XLU/XLI/TLT/SLV) that broaden the book away from its tech/crypto tilt, Tier 2 active (AMD/META/AMZN/PLTR/UBER/CRM/COIN/…), Tier 3 speculative/high-IV (SOXL/LABU/TSLL/DPST/MARA/MSTR/RKLB/…). The `sectors:` map groups every name for the per-sector concentration cap. An optional `strike_bands:` map sets per-symbol ±band overrides for the chain scanner (N6) — used for extreme-IV leveraged ETFs so their ~0.25-delta strike is in scope even before IV history exists. Leveraged ETFs (and CC-only thematics like ARKK/BITO) are in `indexes` only — never `would_own`. |
| `scoring_weights.yaml` | How much weight IV rank, technicals, fundamentals, and liquidity each get when ranking candidates. Also `min_candidate_score` (option-candidate floor) and a `buy_to_own:` block (`min_score`, `max_candidates`) governing the buy-to-own screen. **`zone_fit` (default 0.0 = off):** *not* a block weight — it is a blend **inside** `technical`, mixing regime alignment with how well the strike sits in the ideal band (`fair_value.zone_fit_score`). `engine/scoring.py` excludes it from the block-weight normalization sum (`_NON_COMPONENT_KEYS`) so raising it can't silently dilute every real weight. At 0.0 scoring is bit-identical to before the ideal-zone feature. |

**Rule:** Secrets (passwords, tokens) never go in these files. They go in `.env`.

### `src/ibkr/` — The IBKR connection layer

Handles everything that talks directly to Interactive Brokers via the `ib_async` library.

| File | What it does |
|---|---|
| `connection.py` | Opens and manages the connection to TWS/Gateway; enforces one connection per process. Provides a sync (`connect`) and async (`connect_async` / `async with`) connect with backoff, plus `AutoReconnect` — attached to the long-running daemons (approval service, monitor) it listens on `disconnectedEvent` and reconnects with capped backoff (re-subscribing market data on the monitor) so a TWS drop doesn't silently kill them. `connect_with_retry(ib, …, label=)` is a shared startup-connect helper: `connectAsync` wrapped in bounded exponential backoff (reuses `ibkr.reconnect.*`) so a fast stop→start cycle, where IB Gateway still holds the prior session's clientId (`Error 326` "client id is already in use"), self-heals instead of permanently disabling that connection (the 2026-06-24 03:42 case where `/account`/`/status` went dark). The approval service's exec + scan connections and the monitor connect through it. |
| `market_data.py` | Fetches live quotes, option chains, Greeks (delta/theta/IV), and historical IV data. Provides both a sync API and an `async` chain fetcher (`get_option_chain_quotes_async`) — the orchestrator uses the async one so every IBKR call runs on the `ib_async` event-loop thread (never a worker thread), respecting the line-limit batching. The strike band is **IV-scaled** (N6): `_strike_band_pct` returns `max(strike_band_pct, strike_band_iv_mult · IV · √(DTE/365))` from the symbol's latest stored IV (or a `universe.yaml → strike_bands` per-symbol override), so high-IV names widen enough to surface their ~0.25-delta strike instead of being clipped by a fixed ±15%. The auto-computed band is capped at `strike_band_max_pct` (S8) so an extreme-IV ETF can't generate a runaway strike/batch count; an explicit per-symbol override is exempt from the cap. **Qualification-storm guard:** after band-filtering, `_cap_strikes` keeps at most `max_strikes_per_symbol` strikes (nearest spot) so the `strikes × expirations × 2` cartesian can't explode, and `qualify_options_async` (in `contracts.py`) qualifies that cartesian in `chain_batch_size` **chunks**, paced by `request_throttle_seconds`, each bounded by `qualify_timeout_seconds` — a single 768-contract `qualifyContractsAsync` burst of mostly-nonexistent weekly strikes is what flooded IBKR with `reqContractDetails`, tripped a pacing lockout, and (when the outer `symbol_timeout` then cancelled it mid-flight) wedged the whole ib_async session on 2026-06-22. **Line-leak guard:** every `reqMktData` line (option batches *and* spot snapshots) is opened/closed through `_open_line`/`_close_line`, which register the line in a module-level `_OPEN_LINES` table; `drain_market_data_lines(ib)` cancels every still-open line and is called by the orchestrator after any symbol times out or errors, so a fetch interrupted between opening and cancelling a line can't leak it against the ~100-line cap. **Half-dead-socket probe:** `probe_market_data_health(ib)` fires one fully-bounded snapshot quote on `health_probe_symbol` (qualify + tick-wait both timeout-capped, line always reclaimed) and returns `False` if no tick arrives — the intraday loop calls it before each cycle because `ib.isConnected()` can't distinguish a live farm from a half-dead socket whose data requests silently never tick. **Scan-efficiency (S3/S7):** the async path centres the strike band on `_resolve_spot_async`, which prefers `price_data.get_ohlcv`'s latest cached daily close (free after the first scan) and only falls back to a dedicated `reqMktData(snapshot=True)` when no cached close exists — skipping a ~2s spot snapshot per symbol per intraday cycle. Per-batch quote waits and the spot-snapshot wait are **event-driven** via `_await_ready`: they return the instant ticks populate (a well-behaved batch in ~0.2–0.5s) with the old fixed `quote_sleep_seconds`/2s as a *ceiling*, not a floor. Greeks are not waited on (absent on delayed/paper data; the Black-Scholes fallback fills them), preserving the speedup on the target account. Cancel-between-batches line-cap discipline is unchanged. **Greeks fallback is layered IBKR-first (S2):** `_ticker_to_quote` takes the delta/IV from the first available IBKR per-contract computation (`modelGreeks` → `lastGreeks` → `askGreeks` → `bidGreeks` via `_pick_greeks`) so a momentarily-missing model tick still yields *genuine* IBKR greeks; quotes that have an IBKR IV but no delta are BS-filled locally by `_enrich_greeks_from_ibkr_iv` (no network); only quotes IBKR could value *neither* greeks nor IV for fall through to the expensive `_enrich_greeks_yf` Yahoo download (now instrumented — it logs how many quotes forced a Yahoo fetch and how long it took). The scan batch requests generic ticks `101,106` (option OI + implied vol) to capture the IBKR IV. Any BS-derived delta is labelled `greeks_source="black_scholes"` (never `"ibkr"`), so the F6 live-execution gate still rejects it as untrusted live greeks. |
| `portfolio.py` | Reads your current positions, account balance, buying power, and margin. `enrich_positions_with_greeks_async` populates option-position deltas from live model greeks (used by the EOD net-delta-exposure metric, which would otherwise read 0). |
| `contracts.py` | Builds valid IBKR contract objects for stocks and options; runs `qualifyContracts` to validate them |

### `src/analytics/` — The analysis layer

Computes signals that determine whether a trade is worth taking.

| File | What it calculates |
|---|---|
| `iv.py` | **IV Rank** (how high is current implied volatility vs. the past year?), **IV Percentile**, term structure slope, put/call skew, **VRP** (Volatility Risk Premium = current IV% − HV30%; positive means options are pricing in more vol than realized, which is the premium seller's edge), and **IV/RV ratio** (`current_iv / realized_vol` over the configured window, C1). HV30 (`_compute_hv30`) derives from the shared `price_data.get_ohlcv` settled-close history. The IV/RV ratio uses `realized_vol.compute_realized_vol` (configurable window, default 20d) and is exposed on `IVStats.iv_rv_ratio`. |
| `realized_vol.py` | **Close-to-close annualized historical volatility** over a configurable window (C1). `compute_realized_vol(symbol, window=20)` reads the same `price_data.get_ohlcv` OHLCV store, computing log-return std × √252 × 100. Returns None when history is insufficient or computation fails — callers treat None as "data unavailable" and never block on it. Used by `iv.py` to compute `IVStats.iv_rv_ratio`. |
| `market_conditions.py` | **The macro backdrop**, fetched once per scan (not per symbol) and returned as a `MarketConditions` schema attached to `ScanResult`. Four keyless reads: **VIX** (`^VIX`) and the **VIX term ratio** (`^VIX/^VIX3M` — above 1 is backwardation, i.e. near-term risk priced above 3-month, exactly when a naive IV-rank screen most misleads a premium seller); the **10-year yield** (`^TNX`, which quotes ×10) with its 5-session change in basis points; the **SPY 5-session return** off the shared OHLCV store; and **broad-market headline tone**, a VADER read over SPY/QQQ headlines reusing `sentiment._fetch_news` so there is one headline pipeline rather than two. `render_macro_context()` emits the `MACRO BACKDROP` prompt block (single-ticker deep-dive only — the full-universe prompt stays compact); `vix_regime()` is the shared 15/20/30 threshold table the prompt uses. VIX/VIX3M are fetched per scan (cheap, intraday-moving); rates, tape, and headlines are `@daily_cached`. Every field degrades to `None` independently. Enrichment only — asserted by `tests/test_eval_skills.py::test_macro_never_reaches_the_engine`. |
| `fair_value.py` | **Where a short option ought to be written, and for how much.** `compute_ideal_zone(...)` returns an `IdealZone`: (1) an **expected move** `spot · IV · √(DTE/365)`; (2) a **strike band** 0.30–1.20σ out, snapped to the symbol's own support/resistance (the first consumer of `TechnicalStats.support_levels`/`resistance_levels`, computed every scan and previously read by nothing), anchored to a 50d/200d SMA inside the band, widened for earnings-inside-DTE and a failed quality screen, nudged up for an ex-div inside a covered call's life, and floored at `cost_basis × min_strike_vs_basis`; (3) a **minimum credit** — Black-Scholes fair value at *realised* vol (HV30) plus `min_credit_edge_pct`, never below what the ROC/annualized-yield gates imply — making the variance-risk-premium thesis explicit. `compute_ideal_zone` prices this at the band's **anchor** strike (the right number for the abstract band); callers holding a specific contract must re-price it with **`zone_for_contract(zone, strike, iv, *, cost_basis)`**, which returns a copy whose `min_credit` is priced at the strike actually on offer and whose ROC/yield component divides by the denominator the strategy's gate really uses (cost basis for a CC, strike for a CSP). Both CC and CSP generators call it per candidate — comparing an offered premium against the anchor's floor mislabelled every strike away from the anchor (a $250C at $2.31, twice its own $1.13 floor, read "below fair value"). The band itself is strike-independent and stays memoized per DTE; (4) **action levels** (the spot at which the anchor sits mid-band — the band's own midpoint multiplier, not a hard 1σ, so a well-placed contract isn't flagged as needing a better entry — and a share-acquisition `buy_below` — the **nearest** level below spot among support, the 50d SMA, the analyst mean target less a margin of safety, and the lower quartile of the 52-week range; anchors at or above spot are discarded, and the deeper ones stay visible in `buy_anchors` ordered nearest-first. Taking the *minimum* instead would usually surface the 52-week quartile, ~25-30% below spot — technically conservative and operationally useless). `zone_fit_score()` is the optional ranking hook wired into `_scoring.technical_score` under the `zone_fit` weight (**ships at 0.0** — display-only by default). Fully fail-soft, never raises, and this module itself **never gates** — it only computes and returns numbers. (D2) `min_credit` is now also read by `risk_engine.validate_candidates` and by both generators as the primary income gate (`income.require_vrp_edge`, reason `premium_below_fair_value`): the Rules Engine, not `fair_value.py`, is what rejects — this module has no reject path of its own, so the "Rules Engine is the sole path to an order" invariant is unchanged. ### `src/strategies/` — Trade candidate generators

Each module takes the analytics data and generates specific trades you could place.

| File | What it generates |
|---|---|
| `covered_call.py` | Covered call candidates: for each stock you own, finds the best call strike to sell (target delta, expiry, annualized yield). `screen_cc_candidates(...)` is the full screen returning a `ScreenResult` (passed **+ rejected + skip reason**); `generate_cc_candidates(...)` is the thin wrapper returning only the passing slate. |
| `cash_secured_put.py` | Cash-secured put candidates: for `would_own` stocks, finds put strikes that offer good yield without excessive assignment risk. **Sized to headroom, not to the maximum affordable lot (D1):** `screen_csp_candidates(..., *, positions=None)` calls `engine.capital.resolve_caps`/`seed_budgets`/`max_contracts` — the same helper the Rules Engine uses — so contract count is the largest lot that fits every cash and concentration constraint at once (cash, per-ticker/sector risk units, the large-position slot), rather than the min of cash-and-CSP-budget alone; the two paths can no longer disagree about how big a position may be. `positions` seeds the running budgets from what the account already holds (both `scan.py` call sites pass the current snapshot; omitted it defaults to an empty portfolio). When no size fits at all, the candidate still renders at a display-only 1 lot tagged `insufficient_cash` (cash was the binding constraint) or `no_headroom` (a concentration/budget cap was) — the reason names which. Same `screen_csp_candidates` / `generate_csp_candidates` pairing as above. |
| `_evaluation.py` | Shared plumbing for screens that report **why** a contract was rejected. `ScreenResult` carries `passed`, `rejected` (`(candidate, reason_codes)`), `evaluated`, and `skipped` (set when the symbol never reached the per-quote loop at all — `not_in_would_own`, `no_long_shares`, `shares_already_covered`), plus a `tally()` for the diagnostic log. `rank_rejects(...)` orders rejects closest-to-passing: fewest distinct failed gates, then nearest the delta-band midpoint, then highest ROC. `display_premium(...)` prices a contract we only intend to *display* (falling back past `strict_mid` where the trading path never would — the accompanying `no_two_sided_market` reason marks it untrusted). Reason codes deliberately reuse the risk engine's vocabulary where the meaning matches, so one `_REJECT_REASON_LABELS` table humanizes both stages. **Every quote is evaluated against all gates rather than short-circuiting on the first failure**, so a reject carries its complete failure list and the ranking is meaningful. |
| `rolling.py` | Roll candidates: for existing short options approaching expiry or breaching delta limits, suggests the best roll-forward trade. Roll credit uses a **live quote** for the current contract; if no live quote is found the candidate is skipped. `generate_roll_candidates(..., *, defensive: bool = False)` runs **two separate economics (D4)**: the default **income** path rolls an unchallenged position forward and still requires a net credit clearing `income.min_roc_pct`/`min_annualized_yield_pct`; `defensive=True` (passed by every monitor-triggered caller, via `roll_pipeline.queue_roll_for_approval`) is for rescuing a challenged, deep-delta short — it skips the ROC/yield tests entirely and instead permits a bounded net debit (`monitor.roll_defensive.max_debit`), requires the new leg to cut `|delta|` by at least `min_delta_reduction`, and (when `require_breakeven_improvement` is set) requires the new strike to improve the breakeven whenever the roll isn't itself a credit. Requiring 1% ROC from a defensive roll made the candidate list empty exactly when the monitor's roll trigger fired, since a 0.60-delta short usually cannot be rolled to a safer delta for a credit. Both paths still populate `TradeCandidate.ideal` (Task 5's D2 follow-up), so the risk engine's variance-risk-premium gate reaches ROLL candidates regardless of which economics produced them. DTE is computed from `market_hours.today_et()`, not local `date.today()` — the earlier local-date read could fire `should_roll` a day early for an operator east of US/Eastern. |
| `buy_candidates.py` | Buy-to-own candidates: stocks from the watchlist worth buying specifically so you can sell covered calls against them. Scores each on IV rank, fundamental quality, and technical regime, then applies a score floor and count cap (`scoring_weights.yaml → buy_to_own.min_score` / `max_candidates`) so it surfaces only the strongest few — without the floor it returned every non-held, non-bearish universe name (e.g. 46/46 over a weekend). Also enriches each with price/IV/HV/VRP/RSI/SMA/earnings/dividend, an estimated monthly CC yield, a deterministic rationale, and the `sector` tag looked up from `universe.yaml → sectors` (used by `format_buy_list` to group candidates by sector). |
| `_scoring.py` | Shared scoring helpers used by all strategy modules. `technical_score` aligns regime to **short** premium (we sell): BULLISH favours selling puts (CSP), BEARISH/SIDEWAYS favours selling calls (CC) — the opposite of buy-side alignment. `fundamental_score` is a quality/dividend step function. `make_candidate_id` is a deterministic, **date-free** hash of `strategy\|underlying\|right\|strike\|expiry` (the property that lets the 15-min loop dedupe via `has_active_order`). `technical_score` also takes an optional `IdealZone` and blends in `fair_value.zone_fit_score` under the per-strategy `zone_fit` weight — the "support/resistance proximity" that `scoring_weights.yaml` has always described but never implemented. `zone_fit` **ships at 0.0**, so the default output is bit-identical to the regime-only score; enabling it is a deliberate human config change. |

### `src/engine/` — The decision and safety layer

This is where candidates get ranked and filtered.

| File | What it does |
|---|---|
| `capital.py` | **Capital arithmetic (D1, Task 9's `portfolio:` block consumes this).** Pure functions, no I/O, no config reads — callers pass the resolved `risk` dict. `risk_units(collateral, current_iv, dte)` computes capital-at-risk over the option's life (`collateral × IV × √(DTE/365)`; `current_iv` is a **percent**), returning `None` when IV is unavailable so callers fall back to a stricter raw-collateral cap rather than treating the position as risk-free. `resolve_caps(account, risk) -> Caps` resolves `risk_limits.yaml → portfolio` percentages into absolute dollar limits for one account snapshot, in a **fixed, non-configurable order**: the cash reserve (`cash_reserve_pct` / `cash_reserve_absolute`, greater-of) comes off `account.excess_liquidity` first, and the CSP budget (`max_csp_allocation_pct_of_deployable`) is a percentage of what remains — expressing both against gross cash would let the two knobs contradict each other. `seed_budgets(positions, sector_of, iv_of=None) -> Budgets` seeds running tallies from current positions (a short put charges its assignment liability, matching how a new CSP candidate is charged). A position snapshot carries no IV of its own, so the optional third argument is a per-symbol IV lookup: supply it and **option** positions also charge the risk-unit tallies (`ticker_risk`/`sector_risk`) at their own DTE — without it those tallies start empty, and existing exposure counts for nothing against the per-ticker/per-sector concentration caps on the (common) path where the *candidate's* own IV is known. Callers that already hold portfolio-wide IV pass it (the full scan sweep via `risk_engine.validate_candidates(..., iv_by_symbol=...)`, `scripts/capacity_report.py`); callers where it would cost a fresh network round-trip on a latency-sensitive path (the order-approval re-validation gate, a single-ticker `/scan SYM` deep-dive) deliberately do not. Stock positions never get risk-unit seeding (no natural DTE) and neither does an expired or IV-less option — those, and every caller that omits `iv_of`, charge the raw-collateral tally only. `max_contracts(...) -> (contracts, binding)` is the single helper both `strategies/cash_secured_put.py` and `risk_engine.py` call to find the largest lot that fits every constraint at once (cash, CSP budget, ticker/sector risk units, the large-position slot) — sharing one helper is what makes the generator/gate disagreement that caused D1 unrepresentable. `charge(...)` mutates a `Budgets` in place so later candidates in the same batch see reduced headroom (the same greedy cumulative-consumption model the risk engine has always used, extended to risk units and the large-position slot). |
| `scoring.py` | Normalizes raw analytics scores (IV rank, RSI, etc.) into a 0–100 scale |
| `decision_engine.py` | Combines scores with the configured weights, ranks candidates by total score, and selects the top N. `select_top_candidates_detailed(...)` returns `(top, dropped)` where each dropped candidate carries **why** — `"dedupe"` (a better strike on the same name won the slot) or `"top_n"` (`max_new_positions_per_run` was already full). Both used to vanish silently, making a full slate indistinguishable from a gated-out one; `select_top_candidates` remains as the thin wrapper. |
| `risk_engine.py` | **The safety gate.** Checks hard limits and returns PASS/REJECT with reasons. No AI. `validate_candidates` is **portfolio-aware**: it walks the ranked batch in priority order and enforces *cumulative* limits via `engine.capital` — deployable-cash feasibility, per-ticker/per-sector concentration in **risk units** (`max_risk_units_per_ticker_pct`/`max_risk_units_per_sector_pct`, falling back to raw-collateral `max_collateral_per_ticker_pct` when IV is unknown), the large-position slot, and total cash-secured-put collateral against the deployable-cash CSP budget — so multiple candidates can't each claim the whole account (D1, Task 9; see the `risk_limits.yaml` `portfolio:` block above for the full key reference). The optional `iv_by_symbol=` argument is forwarded to `capital.seed_budgets` so the account's *existing* option positions charge those risk-unit budgets too, instead of the batch's candidates only being measured against each other; the full scan sweep passes the IV map it already computed, and the two paths that would have to buy that data with a new network call (the order-approval re-validation gate, the single-ticker deep-dive) omit it by design. It also gates per candidate: the variance-risk-premium floor (D2, primary — `income.require_vrp_edge`, reject when `premium < candidate.ideal.min_credit`, reason `premium_below_fair_value`; a missing ideal zone never blocks), ROC/yield noise floors (`income.min_roc_pct`/`min_annualized_yield_pct`, now secondary — see `fair_value.py` below for why), IV-rank floor (when known), DTE window, delta (required for income strategies), and the earnings blackout. **Those three income gates (ROC, annualized yield, VRP) apply to the income strategies only.** A `Strategy.ROLL` is a repair, not an income trade: a defensive roll books `roc_pct = 0.0` by construction and pays a premium deliberately under the new strike's fair value, so leaving rolls inside the gates rejected *every* defensive roll — structurally, at the approval-queue re-gate in `execution/approval.py`, after the operator had already approved the card. A roll's economics are bounded by `strategies/rolling.py`'s own `monitor.roll_defensive` knobs (`max_debit`, `min_delta_reduction`, `require_breakeven_improvement`); its `ideal` zone stays populated and visible on the card as display/audit. `validate_live_quote` is the second pass at execution time, re-checking a single candidate against the fresh live quote (delta drift / collapsed mid). |

### `src/execution/` — Order placement

Handles everything between your Telegram approval and the order reaching IBKR.

| File | What it does |
|---|---|
| `order_builder.py` | Builds the IBKR order objects (never market orders). `build_limit_order`: a single-leg mid-price SELL, rounded to the penny-pilot tick ($0.01 below $3.00, $0.05 at/above). `build_combo_roll_order`: a two-leg **BAG combo** (BUY-to-close old short + SELL-to-open new short) priced at the net — a credit roll is a *negative* net-debit limit (`lmtPrice = -net_credit`). `reprice_limit`: pure chase-price helper — steps a resting limit a fraction toward the bid (SELL) or ask (BUY), tick-rounded and guarded by a floor/ceiling. |
| `executor.py` | Places single-leg (entry SELL) orders via IBKR, monitors for a fill, handles timeouts and cancellations, records the fill (with entry IV) and the `filled` learning-loop outcome. A `ROLL` candidate is delegated to `roll_executor.execute_roll`. When `execution.reprice_enabled` is set, the fill-wait loop chases an unfilled SELL down toward the bid (via `reprice_limit`) up to `max_reprices` times — never below `min_live_premium_ratio × approved premium` — before cancelling on timeout. Each chase step **re-fetches the live bid/ask** (`_refetch_bid_ask`, N11). `_refetch_bid_ask` and `_as_float` are shared helpers also imported by `position_manager` and `roll_executor` for their own reprice loops. |
| `roll_pipeline.py` | **Wires rolls end-to-end** (N20): `queue_roll_for_approval` takes a triggered short + a fresh chain, calls `generate_roll_candidates(..., defensive=True)` — every roll this pipeline generates originates from a monitor trigger, so it is judged on risk reduction, not yield (D4) — persists the best as a `CandidateRow`, and raises a PENDING `ApprovalRow` (frozen snapshot, N2a). Approve then creates a QUEUED ROLL `OrderRow` → `process_queued_orders` → `execute_candidate` → `execute_roll`. Called from the monitor's `fire_alerts` only when `monitor.roll_execution_enabled` is set (default OFF, pending live BAG-sign verification); otherwise rolls stay alert-only. `validate_candidates` treats ROLL as exposure-neutral so the queue re-gate doesn't double-count the replaced leg. |
| `roll_executor.py` | Executes a `Strategy.ROLL` candidate as one atomic BAG combo. Resolves the existing short to buy back from live positions, fetches fresh quotes + qualified conIds for both legs, re-gates the new leg via `validate_live_quote` plus a **net-credit floor** (`min_live_premium_ratio`), requires a LIVE-mode [CONFIRM LIVE] tap, places the combo, cancels on timeout, and records two FillRows (BUY under the original short's `candidate_id`; SELL under the new id). **C5:** when `execution.reprice_enabled` is set, the fill-wait loop re-fetches per-leg bid/ask, recomputes the live net credit, and steps the BAG net-limit toward market (ceiling: `min_live_premium_ratio × approved credit`). The combo sign convention is mock-tested only and is on the STATUS.md live-verification list. |
| `approval.py` | Picks up QUEUED orders → re-validates against the Rules Engine (batched, cumulative-aware) → hands off to executor. `_load_candidate` executes the **frozen approved snapshot** on the OrderRow (N2a), never the latest `CandidateRow` payload, so a 15-min re-scan that mutated `contracts`/`premium` between approval and execution can't change the size the human approved (legacy snapshot-less rows fall back to `CandidateRow`). |
| `profit_take.py` | **Exit orchestration** (extracted from the notify layer, N23): loads short positions, computes entry credit (`net_entry_credit_per_share`, qty-weighted SELL fills less commission), and checks two independent exit triggers: `check_profit_takes` at the 50% threshold, and `check_loss_exits` when cost-to-close reaches `max_loss_multiple` (default 2.0×) the entry credit. Both share a common `_quote_short` helper (N14 — polls for a two-sided tick in 0.1s steps, returns early once a market arrives rather than burning full quote timeout per position). Both either auto-buy-to-close (via `position_manager`, when `automation.auto_close_enabled` is true) or send an alert (when false) — independent of the autonomy rung, since closing risk should never wait for a tap; `check_loss_exits` additionally needs `automation.max_loss_multiple`. ### `src/backtest/` — Offline income backtest

A standalone, deterministic simulator for the CC/CSP income strategies. It is **fully isolated
from the live path** — it imports nothing from `engine/` or `execution/` and is never imported by
them — so it can never influence a real order. **v1** synthesises premiums with Black-Scholes from
trailing realised vol (a fair-value IV proxy → expected edge ≈ 0 by construction). **v2 (N21)**
prices the entry premium from the symbol's *stored* daily IV (`iv_history`), so the result actually
measures the variance-risk premium (IV−HV); it also simulates the 50% profit-take and IV-rank
gating. Use it to compare parameter choices, not as tick-accurate truth.

| File | What it does |
|---|---|
| `engine.py` | The pure core. `simulate(symbol, prices, params, *, iv_series=None)` walks a daily-close series, writes non-overlapping short-premium cycles, settles each cash-style at expiry, and returns a `BacktestResult`. With `iv_series` it prices entries at the stored IV (measuring VRP) and reports `mean_vrp_pct` + `iv_source`; `params.profit_take_pct` closes a cycle early when its daily mark decays to the take level (`profit_take_rate`); `params.min_iv_rank` only opens cycles whose backtest IV rank clears the bar. Takes in-memory series → unit-testable offline. |
| `data.py` | yfinance loaders: `load_price_series` (daily closes), `load_iv_series` (forward-filled `iv_history` IV aligned to the price dates, the v2 entry-IV source), and **C10** `load_earnings_dates` (returns sorted historical earnings dates from `ticker.earnings_dates`; empty list for ETFs / network failures, never raises). Kept out of `engine.py` so the core needs no network/DB. |
| `report.py` | Plain-text renderers for the CLI. `format_report` — full `BacktestResult` summary (pricing-IV source, mean VRP, profit-take rate). **C11** `compact_report` — 4-line summary of a `BacktestResult` suitable for injecting into Claude prompts or displaying at decision time. **C10** `format_earnings_cycle_report` — human-readable summary of an `EarningsCycleBacktestResult`. |
| `earnings.py` | **C10** Earnings-cycle backtest + vol-crush mode. `simulate_earnings_cycles(symbol, prices, params, earnings_dates, *, blackout_before, blackout_after, vol_crush_dte, iv_series)` segments the price series by historical earnings dates and evaluates strategy performance across each inter-earnings window, gating entries when the window is too narrow for the DTE. The optional vol-crush mode also enters a short-DTE trade right after each earnings release while IV is still elevated. Returns an `EarningsCycleBacktestResult` with per-cycle detail (pre-earnings trade, vol-crush trade, gate flag) and aggregate win-rate / P&L. Pure and offline: takes in-memory series, never touches the DB or network. |
| `on_demand.py` | **C11** Reusable, candidate-aware core behind the CLI **and** the strategist-prompt injection. `params_from_candidate(cand, *, profit_take_pct, min_iv_rank)` maps a live `TradeCandidate`'s delta/DTE/contracts into `BacktestParams`; `run_backtest(symbol, params, *, …, earnings, …)` loads history and runs the right simulation, returning a `BacktestOutcome` (standard / earnings result / human error message — never raises); `summarize(outcome)` and `backtest_candidate(cand)` return a compact text block. **Fence:** enrichment for verdict/ranking only — reaches Claude solely through the prompt builder, never imported by `engine/`, `execution/`, or the sizing path. |

### `src/orchestrator/` — Daily workflows

Ties everything together into the daily automated routines.

The scan is deliberately split three ways, so that *producing* a scan's data and *presenting* it
are separable concerns: `scan_pipeline.py` produces per-symbol data, `scan_progress.py` owns
everything a human sees (both the live progress messages and the end-of-run sends), and `scan.py`
sequences the two, aggregates the run-level state, gates and persists. The load-bearing rule is
that **`scan_pipeline.py` imports nothing from `src/notify/`** — enforced by
`tests/test_eval_skills.py::test_scan_pipeline_does_not_import_the_notify_layer` — so any caller
that only wants a `ScanResult` (the 15-min daemon loop, a future HTTP API) can trigger a scan
without acquiring a Telegram dependency it could never shed.

`scan_progress.py` is intended to be the only module of the trio importing `src/notify/`, and it
holds every Telegram call *except three*: `scan.py`'s module import block still names
`send_candidates`, `send_buy_list` and `send_account_snapshot`, which it injects into
`send_scan_results` as a `SendDeps` bundle. That is a **test constraint, not a design choice** —
`tests/test_scan_timeout.py`, `tests/test_scan_materiality.py` and `tests/test_scan_review_reuse.py`
monkeypatch those three as attributes of `src.orchestrator.scan`, so moving the references would
make the stubs silently miss and let the suite send real Telegram traffic. Same reason
`scan_pipeline.SymbolDeps` injects its screens. (`run_ticker_scan` also imports
`format_ticker_scan_result` function-locally; that path is untouched by the split.)

| File | What it does |
|---|---|
| `eod_report.py` | Spawned by `scripts.start`'s built-in scheduler at 4:15 PM ET (configurable via `scheduler.eod_report`; no cron job needed). Pulls the day's **option premium cashflow** (SELL credits − BUY debits — surfaced as "premium cashflow", not a paired realized P&L; assignment stock-leg P&L is excluded, N13), generates a journal entry via Claude, sends an end-of-day summary to the **account snapshot thread** (thread 58). | `scan.py` | The canonical scan orchestrator shared by the 15-min daemon loop and the on-demand `/scan` Telegram command, and the public entry point of the trio: `run_scan` + `ScanResult` (plus `run_ticker_scan` / `TickerNotFoundError`, which `notify/approval_service.py` imports). In `intraday` mode it also enables the **S5 LLM-skip**: `_candidates_review_hash` hashes the top candidates' `candidate_id` + signal vectors, and when that matches the prior cycle's hash (stored in the `last_review_hash` system setting) the `claude -p` review is skipped and the persisted `ClaudeReview`s are reused via `_load_prior_reviews` — enrichment-only, the risk gate already ran, so this never affects gating (the fence). Manual `/scan` leaves `intraday=False` and always sweeps the full universe, reviews fresh, and sends in full. After the risk gate, `run_scan` also computes per-strategy **near-misses** — the top `_NEAR_MISS_LIMIT` (1) highest-scoring contract that did *not* make `passed` (failed the gate, or cleared it but fell below the score floor), plus a count of any further rejects — and passes them (`near_misses`/`near_miss_more`) to `send_candidates`, so an empty CC/CSP screen on any cycle (including the 15-min loop) names the single closest trade, why it was rejected, and "…and N more" when the rest were truncated. **Single-ticker scan:** `run_ticker_scan(ib, ticker, *, bot, chat_id, progress_msg_id)` is a slimmer on-demand variant for the `/scan AAPL` command: validates the ticker via `qualifyContractsAsync` (raises `TickerNotFoundError` if unknown), fetches the option chain, runs analytics and CC/CSP/buy-candidate generation (CC only if the ticker is held), applies scoring and the risk gate, and edits the Telegram progress message in place with `format_ticker_scan_result`. For any strategy that turned up no qualifying option it identifies the best-scoring *failed* contract (the near miss) and its specific gate reasons (from `scored` — sorted desc — and the verdict map), so the card shows the closest strike and exactly what it failed on. It also derives a `greeks_fallback` flag from the chain quotes for the honest sources footer. And — like the full scan, enrichment-only — it runs the best CC + best CSP through `review_candidates` (the configured Claude/Ollama backend) off-thread for a `🤖` verdict; a review failure is non-fatal and the card simply renders without it. The single-ticker call is a **holistic deep-dive**: the macro/sector backdrop is **always** gathered (off-thread, in parallel: this ticker's prior-recommendation memory `_load_memory([ticker])`, the macro `MarketConditions` via `get_market_conditions`, and the `SectorContext` via `get_sector_context`) regardless of whether any contract qualifies — so the deterministic "🌐 Market & Sector" line never depends on a tradeable trade existing. The LLM "🧠 Read" reviews the best CC + best CSP; **when neither cleared the gate it falls back to reviewing the closest near-miss per strategy** so the deep-dive still produces a synthesis instead of going silent (these near-misses surface only as the overall `summary`, never as a per-candidate verdict — the card shows verdicts only beside a qualifying contract; the `/scan TICKER` path never executes, so the fence is untouched). `review_candidates` is called with `sector_context=...`, `single_ticker=True`, and `analytics=analytics_map` (the per-symbol raw signals). `single_ticker=True` switches the prompt to a gate-neutral framing and additionally requests a plain-English `summary` that *explains what each metric means* and synthesizes sentiment from the VIX regime + sector backdrop. The card renders the deterministic "🌐 Market & Sector" line (VIX regime + sector/SPY/ticker returns + relative strength) and the "🧠 Read" block (the LLM `summary`, shown once). A full sweep also tallies `ScanResult.provenance` (a `ProvenanceCounts`) — per-symbol option-chain success/failure/skip, which source produced each symbol's spot price (IBKR chain parity vs. yfinance), VIX availability, and the IBKR-vs-Black-Scholes split of option Greeks — and sends it as a final `format_data_provenance` Telegram message once the scan completes, so an operator can see at a glance which data sources were live this run. |
| `scan_pipeline.py` | The per-symbol half of a scan, and **data only** — no Telegram, no progress tracker, no run-level state. `scan_symbol(ib, symbol, *, material, account, positions, would_own, probed_spot, symbol_timeout_seconds, deps)` runs one symbol's option-chain fetch (bounded by `symbol_timeout_seconds`, draining leaked market-data lines on timeout/error), spot resolution (`infer_spot_from_quotes`), analytics + sentiment concurrently off-thread, and the CC/CSP screens with `apply_sentiment` stamped onto every contract they produced (passed *and* rejected — both are rendered on the same cards). It never raises: every failure is folded into the returned `SymbolOutcome` — a `ChainStatus` (`SKIPPED` / `FETCHED` / `EMPTY` / `TIMEOUT` / `ERROR`), the passed/rejected candidates, the analytics triple (`None` ⇒ analytics failed, drop this symbol), per-quote Greeks provenance, and an `errors` list of operator-facing strings the caller pushes to whatever progress surface it owns. `ChainStatus` is what lets `scan.py` drive both the provenance tallies and the circuit breaker without this module knowing either exists: only `TIMEOUT` advances the breaker, `SKIPPED` (the S1 gate declined to look) leaves it untouched, and anything else proves the socket answered. External collaborators — chain fetch, analytics, sentiment, the two screens — arrive via the frozen `SymbolDeps` dataclass rather than being imported and called directly, so the orchestrator stays in charge of which implementation runs (and the scan tests keep a single seam to stub). |
| `scan_progress.py` | **All scan presentation** — the live progress messages *and* the end-of-run sends — split out so the pipeline above has no dependency on it. **While the scan runs:** `_Tracker` edits **two** Telegram messages in place: a *checklist* (one line per stage — account, market data, scoring, Claude, notify) and a *dashboard* (a progress bar + ETA, a current-activity line, and a running log of per-symbol errors flagged 🔴). The dashboard's per-symbol updates are throttled (`_DASHBOARD_MIN_INTERVAL`) to stay under Telegram's edit-rate limits; stage changes, errors, and completion always flush. Both surfaces are written through async callbacks supplied by the caller (`_ProgressCB`), either of which may be `None` — the 15-min daemon loop passes neither and runs silently — so the tracker needs no Telegram SDK of its own and a non-Telegram front-end can reuse it by passing its own sinks. **When the scan finishes:** `send_scan_results(tracker, result, *, bot, chat_id, intraday, account, positions, cc_empty_reason, csp_empty_reason, cc_near_misses, cc_near_miss_more, csp_near_misses, csp_near_miss_more, per_symbol_skip, sends)` drives the whole `notify` stage — the CC and CSP candidate cards (with the `_ASSESSED_LIMIT`-capped "assessed but not approved" listing on full sweeps only, S6), the buy list, the C7 skip-reasons card, the best-effort account snapshot, and the full-sweep `format_data_provenance` summary — plus that stage's `tick`/`error`/`complete` transitions. It never raises: the candidate sends are wrapped so a Telegram failure marks the stage failed instead of aborting the scan, and the account snapshot and provenance summary are each independently best-effort. `thread_id` and the three formatters are imported here directly; the three `send_*` coroutines arrive injected via the frozen `SendDeps` (see the note above the table). The empty-screen reason strings are rendered by `scan.py` (`_no_candidates_reason`) and passed in, since they read `ScanResult` plus the per-strategy rejection tallies. |

### `src/storage/` — The database

All data is stored in a SQLite database at `data/income_system.db`.

| File | What it does |
|---|---|
| `db.py` | Database connection and session management via SQLAlchemy. For SQLite it enables WAL mode + a 30 s busy-timeout (so the concurrent processes don't hit "database is locked"), applies a lightweight ALTER-in for columns added after the original schema, and creates partial indexes that the model metadata can't express portably (e.g. `uq_orders_active_candidate` — one working order per candidate). |
| `models.py` | Defines the database tables: `candidates`, `risk_verdicts`, `claude_reviews`, `approvals`, `orders`, `fills`, `iv_history`, `price_history`, `scan_state`, `position_snapshots`, `roll_alerts`, `claude_memory`, `verdict_ledger`, `journal`, `system_settings`, `campaigns`. `scan_state` (unique per `symbol`) is the S1 intraday-materiality store: one row per symbol holding `last_spot` + `last_scanned_at` (at its last option-chain fetch) and a `cleared_floor` flag, upserted for every fetched symbol so the 15-min loop can decide which chains to re-fetch and which to skip. `price_history` (unique per `symbol`+`obs_date`) stores settled daily OHLCV bars backing the technical indicators and HV30, so scans read history from SQLite and only fetch the missing tail from yfinance. `position_snapshots` (unique per `snapshot_date`) holds the daily portfolio JSON the EOD run writes for assignment auto-detection (position diffing). It sat defined-but-unwired for a long time — every rejection was ephemeral — and is now written by `storage/risk_verdicts.py` and pruned to 14 days at EOD. Write-only forensics: no production code reads it, so it can never influence a trading decision. `candidates`, `orders`, and `journal` carry unique constraints to prevent duplicate rows. |
| `system_settings.py` | Helper functions for the `system_settings` table. **Autonomy ladder (Task 14):** `get_autonomy_level()`/`set_autonomy_level()` (persisted under the `autonomy_level` key, default `AutonomyLevel.OBSERVE` — the safe rung for a fresh install), `may_auto_open(symbol)` (True iff not halted and the rung — WHITELIST checks `_autonomy_whitelist()`/`set_autonomy_whitelist()`, backed by the comma-joined `autonomy_whitelist` key; FULL always; OBSERVE/MANUAL never — clears the symbol for auto-open), `promotion_blockers(target)` (empty list ⇒ promotion allowed; demotion is always `[]`; promoting to WHITELIST/FULL is blocked until the account shows >=20 fills, >=60% fill rate, and >=1 `close:`-prefixed buy-to-close `OrderRow`), and `autonomy_progress()` (read-only `(fills, fill_rate, has_closed_once)` tuple for the `/autonomy` status display — the same evidence `promotion_blockers` checks, never itself used to gate anything). Also: the cross-process scan lease (`acquire_scan_lease()`/`renew_scan_lease()`/`release_scan_lease()` — serialises full scans so concurrent `/scan` commands can't compete for the market-data line cap, F5), and `get_setting()`/`set_setting()`. The lease is **owner-token + heartbeat** (N7): `acquire` returns a stable token; the scan loop calls `renew` each symbol to extend the TTL so a long ~60-symbol scan can't expire mid-run; and `renew`/`release` are compare-and-swap, so a scan that overran and was re-claimed can't clobber the new holder. | `orders.py` | Order-creation idempotency: `has_active_order(session, candidate_id)`. | `positions.py` | Daily position-snapshot persistence for assignment auto-detection. `save_position_snapshot(date, positions)` upserts one JSON row per ET day (written by the EOD run); `load_latest_position_snapshot(before=…)` returns the most recent prior snapshot to diff against. |
| `campaigns.py` | **C6 wheel-campaign tracking.** `attach_fill_to_campaign(symbol, candidate_id, strategy, action, avg_price, filled_qty)` — called by the executor after every fill; opens a new campaign on the first SELL, appends candidate IDs to the existing open campaign on subsequent fills, then calls `_rollup` (re-aggregates `total_premium_collected`, `total_debit_paid`, `net_premium` from all `FillRow`s for the campaign's legs) and `_auto_close` (marks the campaign closed when `buy_qty ≥ sell_qty` and not assigned). `mark_campaign_assigned(symbol, assignment_price, right=None)` — sets `assigned=True` and, when shares are *acquired* (short put, or `right` unknown), computes `adjusted_cost_basis = assignment_price − net_premium/100` per share; a short **call** assignment (`right="C"`, shares called away) flags the campaign assigned without altering the basis. The 15-min loop reads this to gate the (expensive) option-chain fetch; the first intraday cycle sweeps all symbols and writes baselines for every one. All failures are swallowed — it is an optimisation, never a correctness dependency (a read miss degrades to "treat as material"). |
| `risk_verdicts.py` | **Assessment audit trail.** `record_assessments(run_id, assessed)` writes one `RiskVerdictRow` per contract the scan priced — approved or not, with the stage it stopped at and the raw reason codes — so "why did NVDA never produce a CSP in July?" is answerable after the Telegram status message has rolled over. `purge_old_risk_verdicts(days=14)` prunes it at EOD. | `iv_history.py` | Accessors for the `iv_history` table (N4): `latest_iv` (most recent IV, used by the IV-scaled strike band), `append_observation` (idempotent daily insert, called from the EOD run so the IV-rank window stays current), and `latest_obs_dates`/`stale_symbols` (powering the `/health` staleness warning). | `price_history.py` | Accessors for the `price_history` table: `load_bars` (settled OHLCV, ascending), `latest_bar_date`, and `append_bars` (idempotent — skips dates already stored). Source for `analytics/price_data.get_ohlcv`; same error-swallowing discipline as `iv_history.py`. |

Every stage of the pipeline writes its results here. This means:
- If a scan crashes halfway through, the next run can pick up where it left off.
- The dashboard reads from this database — no IBKR connection needed.
- You can inspect any trade decision by querying the database.

| `start.py` | `python -m scripts.start` | **Single-command launcher**: starts both always-on daemons (approval service + monitor) as supervised subprocesses with auto-restart on crash, **and schedules the EOD report itself** — at `scheduler.eod_report` (default 16:15 ET) on NYSE trading days it spawns a one-shot `scripts.run_eod` subprocess (no cron job needed). The last-run date is persisted to `data/eod_scheduler_state.json` so a restart after the report has already run does not re-fire it; a start *after* the EOD time on a trading day that has not yet run fires immediately (catch-up). The launcher process holds **no** `ib_async` loop — the EOD job runs in its own subprocess with its own client ID, preserving the "no threaded scheduler inside an ib_async loop" invariant. Accepts `--no-monitor` / `--no-approval` / `--no-eod` flags. On launch, when `claude.backend` uses Ollama, runs `probe_ollama()` and logs a loud WARNING if the local model is unreachable/unpulled — daemons still start (fail-soft: deterministic list, no LLM enrichment), so it never blocks startup. Before launching daemons it pauses `STARTUP_GRACE_SECONDS` (default 4s, `0` disables) so a fast restart gives IB Gateway time to release the prior session's client IDs (avoiding the `Error 326` collision; `connect_with_retry` is the backstop if it still races). |
| `run_eod.py` | `python -m scripts.run_eod` | Runs the EOD report (normally spawned automatically by `scripts.start`'s scheduler; can also be run by hand) |
| `run_approval_service.py` | `python -m scripts.run_approval_service` | Starts the long-running approval + execution daemon |
| `run_monitor.py` | `python -m scripts.run_monitor` | Starts the intraday position monitor |

| `backfill_prices.py` | `python -m scripts.backfill_prices` | One-time: seeds ~1y of daily OHLCV into `price_history` so the first scan reads from SQLite instead of pulling full histories from yfinance. Safe to re-run (only the missing tail is fetched). |
| `reconcile_outcomes.py` | `python -m scripts.reconcile_outcomes` | Reconcile the outcome ledger (deterministic, DB-only). `--assigned <id…>` flags past-expiry shorts that were assigned. Also runs automatically at EOD. |
| `evaluate_scores.py` | `python -m scripts.evaluate_scores` | Score-vs-outcome report (N22): `blended_score` + per-component bands vs realized win rate / mean P&L, plus per-signal correlation, over closed ledger rows. Read-only; informs hand-tuning of `scoring_weights.yaml`. `--since`, `--until`, `--json`. |
| `backtest_candidate.py` | `python -m scripts.backtest_candidate --symbol AAPL --strategy cash_secured_put --delta 0.30 --dte 30` | **C11** On-demand per-candidate backtest. Accepts `--compact` (4-line output for Claude injection), `--earnings` (C10 earnings-cycle mode with `--blackout-before`, `--blackout-after`, `--vol-crush-dte`), `--profit-take`, `--min-iv-rank`, `--period`/`--start`/`--end`. |
| `capacity_report.py` | `python -m scripts.capacity_report --net-liq 300000 --cash 100000` (hypothetical) or `python -m scripts.capacity_report` (live account via IBKR) | Read-only account-sizing diagnostic: one row per `would_own` symbol answering "how many contracts fit right now, and what stops the next one." Calls `engine.capital.resolve_caps`/`seed_budgets`/`max_contracts` — the same helpers the gate and the CSP generator use — with a **fresh** `seed_budgets` call per symbol, so each row reports what that symbol could do *on its own*, not what's left after other candidates already claimed budget (the real scan consumes one shared, greedily-charged `Budgets`; this report deliberately does not). Strike is approximated at 0.90× spot (a stand-in for the ~0.25Δ put the screens target) — a capacity estimate, not a live quote. `binding` names the first constraint that would stop the *next* lot (`cash`, `ticker_risk`, `sector_risk`, `csp_budget`, `ticker_collateral`, `large_slot`, `large_ceiling`), or is empty when the per-candidate `cash_secured_put.max_contracts` hard cap was hit with room to spare. `--net-liq`/`--cash` runs the hypothetical branch (skips the IBKR account fetch entirely); omitted, it opens the existing `healthcheck` clientId/role (no new connection) and pulls the real account + positions. Per-symbol IV/price come from `analytics.iv.get_iv_stats` / `analytics.technicals.get_technical_stats`. Each row's `nlv_needed_for_one` is the NLV at which *that ticker's own concentration cap alone* would admit one lot — mirroring `capital._fits`'s own choice of cap: the risk-unit cap (`max_risk_units_per_ticker_pct`) when `current_iv` is known, since that is what actually gates a first lot once IV is present, and the raw-collateral cap (`max_collateral_per_ticker_pct`) only in the no-IV fallback path; it ignores cash, the CSP budget, and sector risk, so it answers "is this ticker's own cap the binding NLV floor," not "what NLV clears every constraint." The printed table also states its own coverage explicitly — `Coverage: N/M requested symbols had usable price/IV data (K skipped for missing data)` — so a data outage that silently drops symbols from the table can never be mistaken for a smaller-but-still-valid tradeable fraction. This is the tool behind `tests/test_account_sizing.py` — the regression class the suite lacked: not "does the gate reject what it says it rejects" but "given this account and this universe, is the tradeable set non-empty and sane," the blind spot that let a 1-lot CSP silently require `NLV >= 2000 x strike` (D1) and a flat ROC floor silently exclude every low-vol name (D2) both pass CI for months. Never places, sizes for execution, or gates an order. |

## Process architecture (what runs where)

The system splits into separate processes, each with its own IBKR client ID, to avoid conflicts.
The full registry lives in `config/settings.yaml → ibkr.client_ids`; **never reuse an id across two
processes that run at the same time.**

| Process | When it runs | Client ID | What it owns |
|---|---|---|---|
| `eod_report` | One-shot at 4:15 PM (spawned by `scripts.start`) | 16 (`eod`) | P&L + journal → Telegram (account snapshot thread) |
| `intraday_monitor` | Always-on during market hours | 12 (`monitor`) | Live position watching + roll alerts |
| `backfill_iv` | One-time manual | 13 (`backfill`) | Historical IV data seeding |
| `backfill_prices` | One-time manual | — (no IBKR; yfinance) | Historical OHLCV seeding into `price_history` |
| `approval_service` | Always-on daemon | **14 (`exec`) + 15 (`scan`)** | Telegram callbacks + order execution (14) and a second connection for `/scan`, `/positions`, `/account`, `/status` (15) |
| `healthcheck` | Manual | 19 | Connection check / account print |
| `trading_skills` MCP | Inside `claude -p` (opt-in) | 20 | Ad-hoc Claude lookups (see `STATUS.md`) |
| dashboard | Optional Streamlit (archived to `Archive/dashboard/`) | 21 | Read-only views (reads SQLite; rarely hits IB Gateway) |

One-shots connect, work, and disconnect; the daemons run continuously and self-heal on a dropped socket via `AutoReconnect`.

## Data flow between modules

All modules exchange data through the Pydantic schemas in `src/common/schemas.py`. The key objects:

| Schema | What it represents |
|---|---|
| `PositionSnapshot` | A current open position (symbol, quantity, cost basis, and `delta` when enriched) |
| `AccountSnapshot` | Account totals: net liquidation, cash, buying power, margin, excess liquidity |
| `OptionQuote` | A single option contract's live snapshot (bid/ask/last, Greeks, IV). Computed fields: `mid` (bid+ask)/2, falling back to `last`; `spread_pct` as a percentage of mid; `dte` as days-to-expiry in ET timezone. |
| `IVStats` / `TechnicalStats` / `FundamentalStats` | Per-symbol analytics outputs. `IVStats` includes `vrp` (IV% − HV30%) and **`iv_rv_ratio`** (C1: `current_iv / realized_vol` over the configured window; None when history is insufficient). `TechnicalStats.price_source` records whether `price` came from `"ibkr"` (chain-inferred spot) or `"yfinance"` (fast_info fallback) — used to build the end-of-scan data-provenance summary. |
| `MarketConditions` | **The macro backdrop**, fetched once per scan and attached to `ScanResult`: `vix`, `vix3m` and the `vix_term_ratio` (VIX/VIX3M — above 1 is backwardation), `ten_year_yield` + `ten_year_change_5d_bp`, `spy_ret_5d_pct`, and `macro_headline_score`/`macro_headline_count`/`top_macro_headline`. All optional/fail-soft. Enrichment only — it reaches the deep-dive card and the prompt, never scoring or the gate. |
| `SectorContext` | **Single-ticker `/scan TICKER` backdrop** (built by `analytics/sector_context.py`): `sector`/`industry`, the SPDR `sector_etf` proxy, 1-month/5-day sector-ETF returns, SPY 1-month return, the ticker's own 1-month return, and `rel_strength_1mo_pct` (ticker − sector). All fields optional/fail-soft. Enrichment only. |
| `ScoreCard` | All analytics scores for a symbol (IV rank, technicals, fundamentals, liquidity, assignment safety). Also carries `sentiment_score` (composite 0-100 `overall`, drives the 5% sentiment weight) and `sentiment_detail` (a `SentimentDetail`, enrichment only). |
| `SentimentDetail` | Composite social + news sentiment for one symbol: `overall` (0-100, 50 = neutral, `None` = no data) + per-source scores/counts (`stocktwits`/`stocktwits_msgs`, `news`/`news_count`, `reddit`), a `label`, 1-day velocity `delta_1d`, and `top_headline`. Produced by `analytics/sentiment.SentimentScorer`; surfaced to Claude + Telegram and logged to the verdict ledger. **Enrichment only — never reaches the risk engine or sizing** (the fence). |
| `TradeCandidate` | A specific trade proposal (symbol, strategy, strike, expiry, premium, scores, and `next_earnings` for the earnings-blackout gate). Carries `price_source` / `greeks_source` for data-source footers; **C1: `iv_rv_ratio`** propagated from `IVStats` — displayed on the Telegram approval card (`IV/RV X.XX`) and gated by the risk engine (`iv_rv_below_minimum`); `current_iv` (IV percent at scan time) feeds risk-unit concentration sizing. Also carries `ideal: IdealZone | None` — where this contract *should* sit versus where it does. |
| `BuyCandidate` | A buy-to-own stock recommendation, enriched from the per-symbol analytics: `score` + sub-scores (`iv_score`/`fundamental_score`/`technical_score`), `sector` (from `universe.yaml → sectors`), `price`, `current_iv`/`hv_30`/`vrp`, `rsi_14`/`sma_50`/`sma_200`, `next_earnings`, `dividend_yield`, and a heuristic `est_monthly_cc_yield`. The `rationale` is a deterministic one-liner built in `buy_candidates.py` (Claude does not review buy candidates — only option candidates). The screen applies a score floor + count cap (`scoring_weights.yaml → buy_to_own`), so it surfaces only the best few names rather than the whole non-held universe. |
| `RiskVerdict` | The Rules Engine's decision: PASS or REJECT, with reasons |
| `IdealZone` | **Where a short option ought to be written, and for how much** (built by `analytics/fair_value.py`): `expected_move`, the `strike_lo`/`strike_hi`/`strike_anchor` band with human-readable `strike_anchors` explaining what moved it, `min_credit` + `credit_anchors` (priced at the *anchor* strike by `compute_ideal_zone`; re-priced at the contract's own strike by `fair_value.zone_for_contract`, which is what the generators attach to a candidate), `action_price`/`action_note` (the spot that restores ~1σ of cushion), `buy_below`/`buy_anchors` (share acquisition), and a `confidence` of high/medium/low reporting how much data the derivation actually had. Attached to every `TradeCandidate` as `ideal`. The strike band and action levels are display + optional ranking only; `min_credit` is also the primary income gate as of D2 (`income.require_vrp_edge`, checked in `risk_engine.validate_candidates` and both generators — reason `premium_below_fair_value`; a `None` zone never blocks). |
| `AssessedContract` | **One contract the scan looked at, and what became of it**: the `candidate`, the `AssessmentStage` it stopped at, and the raw `reasons`. `AssessmentStage` is declared in pipeline order (`generator` → `risk_gate` → `score_floor` → `dedupe` → `top_n` → `passed`), so a stage's position in the enum *is* its "how far did it get" rank — which is what `scan._rank_assessed` sorts on. Collected for every contract priced, so a scan that approves nothing can still show the operator what it saw. |
| `ClaudeReview` / `RollReview` | Claude's structured review of a candidate / a live position roll. `ClaudeReview.summary` is a plain-English synthesis populated **only on the single-ticker `/scan TICKER` path** (the prompt requests it via `single_ticker=True`): it explains what the metrics mean and reads the VIX/sector backdrop into an overall sentiment; empty on the full-universe path. |
| `RollAlert` | A fired intraday trigger (delta drift, DTE, IV spike, ex-div) |
| `EODSummary` | End-of-day metrics handed to Claude and stored in the journal. `date` is the **ET trading day** (so the JournalRow write key matches the yesterday→today baseline read; using local `date.today()` could skew them across UTC offsets and silently zero the unrealized Δ). `top_movers` is the top-3 underlyings by absolute unrealized swing across **all** sec_types (a stock leg can be the day's biggest driver), with `mover_pnl` carrying each one's aggregated P&L for the report's "Drivers" line. `watchlist_changed` is False when tomorrow's watchlist equals yesterday's, letting the report collapse the static 30+ ticker list to a count. |
| `VerdictRecord` | One outcome-ledger entry: the signals Claude saw + its verdict + the deterministic `BaselineDecision` + the back-filled realized `VerdictOutcome`/P&L |
| `ScoreBucket` / `SignalCorrelation` / `ScoreOutcomeReport` | Score-vs-outcome evidence (N22): per-band realized win rate / mean P&L and per-signal correlation against realized P&L, over closed ledger rows |

(The complete, authoritative list is the set of classes in `src/common/schemas.py`.)

## Key invariants (things that must never change)

1. **The Rules Engine is the only path to execution.** Nothing bypasses it.
2. **Claude never places, sizes, or blocks orders.** It enriches; it does not control.
3. **One IBKR client ID per process.** Sharing IDs causes connection conflicts.
4. **Secrets live only in `.env`.** Never in code, logs, or YAML.
5. **All option orders use LimitOrder at mid-price.** Never market orders.
6. **`qualifyContracts` runs before every order submission.**
7. **The fence: the enrichment learning loop never reaches the engine.** `src/claude/eval/` (the
   outcome ledger, close reconciler, and score-vs-outcome analysis) is read-only with respect to
   trading — it observes and measures, never gates, sizes, or ranks. The risk engine, scoring, and
   sizing never import `src/claude/eval/` — gates/weights/limits stay human-edited config. Enforced
   by `tests/test_eval_skills.py::test_skills_never_reach_the_engine`.

## Operational risks & how they're handled

The hard parts of this system are operational, not algorithmic. The main failure modes and their
mitigations:

| Risk | Mitigation |
|---|---|
| **IB Gateway disconnects mid-session** | `AutoReconnect` on the daemons (backoff + re-subscribe); the monitor self-heals on the next poll; one-shots simply abort and retry on the next scheduled run. |
| **Market-data line limit (~100)** | Option chains are requested in batches and cancelled between batches; only one symbol's chain is fetched at a time. |
| **clientId conflicts** | Central registry in `settings.yaml`; one id per concurrent process (see the process table above). On a fast restart, where Gateway still holds the prior session's id (`Error 326`), the daemons connect via `connect_with_retry` (backoff until the id frees) and the launcher waits `STARTUP_GRACE_SECONDS` first. |
| **Claude unavailable / unparseable** | Strict JSON validation + graceful fallback — the Rules-Engine-approved list still ships to Telegram. Claude never blocks the pipeline. |
| **Approval→execution timing gap** | Orders queue in the DB; the executor re-validates against a fresh live quote + the Rules Engine at send time; off-hours orders wait for RTH; stale approvals expire (TTL). |
| **Order rejects / partial fills / wrong contract** | `qualifyContracts` before every order; LimitOrder at mid (never market); fill monitoring with timeout/cancel; rejects alert back to Telegram. |
| **Early assignment (dividends/ITM)** | The monitor flags ITM-ish short calls near ex-dividend and short options breaching delta/DTE, prompting a roll alert. |
| **Risk-limit bypass / runaway** | The deterministic Rules Engine runs twice (decision time + send time); a buying-power buffer is always reserved; live trading is triple-gated. |
| **Secrets leakage** | `.env` is gitignored and never logged; a Telegram chat-id allowlist means only you can approve. |
| **Paper↔live confusion** | Live execution requires `LIVE_TRADING=true` **and** the live port; a loud startup banner states the active mode and account; each live order needs a second `[CONFIRM LIVE]` tap. |

Database concurrency (multiple processes on one SQLite file) is handled with WAL mode + a 30 s busy
timeout, and no process holds a write transaction open across network I/O.
